# 1. Map the ticket flow

Start in [`frontend/src/App.tsx`](../support-ticketing-app/frontend/src/App.tsx), where the user filters the inbox or selects a ticket. `filters` has `query`, `status`, `priority`, `tag`, and `breached`; `selectedId` identifies the current row; `selected` holds a `TicketDetail`. The API adapter in [`frontend/src/api.ts`](../support-ticketing-app/frontend/src/api.ts) turns those values into `/api/tickets` query parameters. It also sends the demo headers `X-User-Id`, `X-User-Role`, and `X-Team-Ids`. Those headers are fixtures, not authentication.

Opening a ticket calls `getTicket(id)` and copies server values into `selected`, `tagDraft`, `assigneeDraft`, and `teamDraft`. Mutations send `selected.version` as `expectedVersion`: `addComment` posts `{ body, visibility, expectedVersion }`, `replaceTicketTags` puts `{ tags, expectedVersion }`, and the status and assignment calls follow the same pattern. The corresponding endpoint map is [`TicketEndpoints.cs`](../support-ticketing-app/backend/SupportDesk.Api/Endpoints/TicketEndpoints.cs). A handler checks the current user policy, passes a mutation into the store, publishes an invalidation, and maps the updated ticket to a detail DTO.

The store is [`InMemoryTicketStore.cs`](../support-ticketing-app/backend/SupportDesk.Api/Infrastructure/InMemoryTicketStore.cs). `UpdateAsync` takes a lock, finds the current ticket, rejects a missing ticket, compares `current.Version` with `expectedVersion`, snapshots the current object, runs the mutation against the working copy, and stores a second snapshot. If the mutation throws, the stored object is never replaced. A successful domain method calls `Touch(now)`, updates `UpdatedAt`, and increments `Version` exactly once.

For an internal comment, [`AddComment.cs`](../support-ticketing-app/backend/SupportDesk.Api/Application/Commands/AddComment.cs) checks `Permissions.CanComment(_user, ticket, request.Visibility)`, invokes `ticket.AddComment`, publishes through [`SignalRTicketNotifier.cs`](../support-ticketing-app/backend/SupportDesk.Api/Realtime/SignalRTicketNotifier.cs), and returns a detail DTO. The notifier sends only the method name `tickets.changed` to group `inbox`; it does not serialize a ticket, customer, or comment. The frontend receives that invalidation and refetches through authorized HTTP paths.

Notice the summary/detail split in [`Dto.cs`](../support-ticketing-app/backend/SupportDesk.Api/Application/Dto.cs). A summary carries `number`, `subject`, customer identity, status, priority, assignment, tags, timestamps, breach flags, `commentCount`, and `version`; it deliberately has no description or comment bodies. A detail adds `description` and the filtered `comments` list. That shape is useful even when the hub is data-free: list refreshes update rows, while detail refreshes reapply the more sensitive comment policy. The frontend types in [`types.ts`](../support-ticketing-app/frontend/src/types.ts) mirror those names, so a renamed C# property requires a coordinated client change and build check.
